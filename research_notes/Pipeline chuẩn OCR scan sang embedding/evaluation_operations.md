# Evaluation, quality gates and operations for OCR → text → embedding pipelines (as of Nov 2026)

Source tags: **[opened]** means the page was fetched and the number read there. **[snippet]** means it comes only from a search-result snippet or a search-tool summary and was not checked on the page. **[pre-2025]** marks older sources.

---

## Q1. What practices are standard in 2025-2026 for quality gates, human review, evaluation at each stage, provenance and operations? Concrete examples

### Takeaway
A mature pipeline does four things. It routes each page or field by confidence, either to a fallback engine or to a human review queue, and also sends a random sample for spot checks. It evaluates parsing with structure-aware metrics: normalized edit distance for text and reading order, TEDS for tables, CDM for formulas, as in OmniDocBench, now at v1.7. It evaluates retrieval and the full RAG system separately (RAGAS-style context recall/precision and faithfulness) against the same question set run on ground-truth text. And it keeps provenance down to page and bounding box. Legal projects add structured markup (Akoma Ntoso/LegalDocML), point-in-time versions keyed on effective dates, and a citation-resolution or audit layer.

### Cited Findings

**Quality gates and routing (confidence thresholds, sampling)**
- AWS Textract + Amazon A2I reference design (2020, **[pre-2025]**, still the canonical pattern). Per-key rules send a field to a human if the "Mail Address" key has confidence below 99% or is missing, and any other key if confidence is below 90%. Each rule has an "identification" threshold and a "qualification" threshold. A third option is "randomly send a sample of forms to humans for review" for model monitoring. The design splits multi-page PDFs into page images, because A2I reviewers work on single pages. Pages are processed concurrently in a Step Functions Map state. A callback task token resumes the workflow after human review, and results are merged and written to S3. **[opened]** — [AWS ML Blog, Nelson/Gupta/Imran, 24 Jul 2020](https://aws.amazon.com/blogs/machine-learning/processing-pdf-documents-with-a-human-loop-using-amazon-textract-and-amazon-augmented-ai)
- A2I sends only predictions below the threshold to reviewers. Thresholds can be changed at any time to trade accuracy against cost, and several workers can be assigned to each review for consensus. **[snippet]** — [AWS A2I features](https://www.aws.amazon.com/augmented-ai/features/)
- Legal-RAG practitioner guidance: use the native text layer first and fall back to OCR only when direct text extraction fails, since OCR is slower and less accurate. If indexing changes documents (e.g. OCR correction), the original must stay queryable for comparison. **[snippet; vendor or blog sources, low authority]** — [reintech.io](https://reintech.io/blog/build-legal-document-analysis-system-llms-rag); [4xxi](https://4xxi-landing.pages.dev/articles/rag-for-legal-documents)
- InduOCRBench (Apr 2026) shows that averaged OCR scores hide failures in specific categories. Category-level failures in ultra-wide pages, ultra-long documents, cross-page tables, multi-column layouts and visual styles such as strikethrough produce large RAG losses even when text accuracy looks fine. One example: removing strikethrough turned a legal clause ambiguous. The paper argues that WER/CER-style metrics miss errors that matter for retrieval. (It does not itself specify gates; any gate design built on it is an inference.) **[opened]** — [arXiv 2605.00911 (InduOCRBench, ACL 2026 Industry)](https://arxiv.org/html/2605.00911)

**Human-in-the-loop: review queues, gold sets, acceptance criteria**
- InduOCRBench annotation QC used a three-stage process with a **98% sampling-audit acceptance threshold**, a concrete example of a sampled acceptance criterion for gold data. Annotation format: Markdown, with HTML tables (rowspan/colspan), LaTeX formulas, and bold/underline/colour preserved. **[opened]** — [arXiv 2605.00911](https://arxiv.org/html/2605.00911)
- OHRBench gold set: 8,561 page images from 1,261 PDFs in 7 domains (Textbook, Law, Finance, Newspaper, Manual, Academic, Administration). It has 8,498 QA pairs filtered from 15,317 candidates. Evidence sources: text 41.5%, table 27.8%, formula 14.9%, chart 9.0%, reading order 8.1%. **[opened]** — [arXiv 2412.02592v3 (ICCV 2025), rev. 16 Aug 2025](https://arxiv.org/html/2412.02592v3)
- Caselaw Access Project (Harvard, ~40M pages from ~40,000 volumes, **[pre-2025]**). Metadata (party names, citation, date) was human-reviewed, but case text was left as raw vendor OCR. The project says there will be "OCR errors on nearly every page" and that it cannot process individual OCR corrections. This is a tiered-quality model: human-verified metadata on top of unverified body text. **[snippet]** — [beSpacific on CAP](https://bespacific.com/?p=104020); [capstone repo](https://www.github.com/rachelaus/capstone)

**Parsing evaluation (CER/WER, edit distance, TEDS, reading order)**
- OmniDocBench (opendatalab). Text is scored with normalized edit distance (plus BLEU/METEOR), tables with TEDS (and TEDS-S for structure only), formulas with CDM, reading order with edit distance, and layout with COCO-style detection mAP/mAR. Overall score (v1.5+) = ((1 − text edit distance)×100 + table TEDS + formula CDM)/3; reading order is **not** part of the overall score. Versions: v1.5 on 2025-09-25, v1.6 on 2026-04-10 (296 new pages, new MGAM matching, CDM about 3× faster), v1.7 on 2026-04-30. Integrated into EvalScope on 2026-07-27. The dataset is 1,651 pages across 10 document types, 5 layout types and 5 languages (per the README). **[opened]** — [OmniDocBench GitHub](https://github.com/opendatalab/OmniDocBench)
- Top of the OmniDocBench v1.6_full end-to-end leaderboard (Overall): OXR-1.0 97.03, TeleOCR 96.91, OvisOCR2 96.47, PaddleOCR-VL-1.6 96.34, MinerU2.5-Pro 95.75 (TeleOCR and OvisOCR2 entries added 2026-09-11). **[opened]** — [OmniDocBench GitHub](https://github.com/opendatalab/OmniDocBench)
- Benchmark scores do not transfer to industrial documents. PP-StructureV3 scores 86.7 on OmniDocBench vs 60.3 on InduOCRBench, GPT-4o 75.0 vs 52.0, and PaddleOCR-VL 92.9 vs 78.2. Hunyuan-OCR table TEDS falls from 91.8 to 52.5. This argues for an in-domain gold set on top of public benchmarks. **[opened]** — [arXiv 2605.00911](https://arxiv.org/html/2605.00911)

**Retrieval and end-to-end RAG evaluation**
- RAGAS metric catalogue (docs page dated 9 Dec 2025). RAG metrics: Context Precision, Context Recall, Context Entities Recall, Noise Sensitivity, Response Relevancy, Faithfulness, Multimodal Faithfulness, Multimodal Relevance. "Answer correctness" now appears as **Factual Correctness** under natural-language comparison. LLM-based metrics may use one or more LLM calls. (The page lists the metrics but does not define them.) **[opened]** — [RAGAS docs – available metrics](https://docs.ragas.io/en/stable/concepts/metrics/available_metrics/)
- InduOCRBench measures downstream effect with FlashRAG (naive pipeline), BGE-M3 retrieval of the top 100 reranked to top 10, GPT-5 generation, and RAGAS Answer Accuracy + Context Recall judged by GPT-OSS-120B. It compares each OCR output with **ground-truth text through the same pipeline** (Δ metrics). Recall@k is not reported. **[opened]** — [arXiv 2605.00911](https://arxiv.org/html/2605.00911)
- OHRBench uses edit distance for OCR quality, LCS of the evidence for retrieval, and F1 for generation. Settings: BGE-M3 and BM25 retrievers, top-2 chunks, chunk size 1,024, with Qwen2-7B/72B and Llama-3.1-8B as generators. Questions whose evidence LCS falls below 0.95 count as "noisy". **[opened]** — [arXiv 2412.02592v3](https://arxiv.org/html/2412.02592v3)
- I did not open a 2025-26 source that sets recall@k/nDCG/MRR thresholds specifically for OCR'd corpora; see Gaps.

**Provenance and auditability (page and bounding box)**
- Docling (IBM, arXiv 2501.17887, 2025). Its output carries page number and bounding-box provenance per element, used for "document-native RAG grounding". The Haystack example prints section, page and bbox for each source chunk. The LlamaIndex example recommends Docling JSON over Markdown because the JSON keeps that metadata. **[snippet]** — [Docling paper](https://arxiv.org/pdf/2501.17887); [Docling Haystack example](https://docling-project.github.io/docling/_generated/examples/rag_haystack/)
- docling-graph keeps a separate `provenance.json` ledger next to `graph.json` for every graph node, with item geometry = page + bbox [l,t,r,b] in page pixels, top-left origin. The geometry is empty for inputs without layout, such as Markdown. Directly relevant to a knowledge-graph target. **[snippet]** — [docling-graph provenance docs](https://docling-project.github.io/docling-graph/fundamentals/graph-management/provenance/)
- IBM watsonx guide (Jun 2025) draws bounding boxes over the original page images as visual evidence for each answer. **[snippet]** — [IBM Community blog](https://community.ibm.com/community/user/blogs/shubham-kumar/2025/06/19/build-rag-with-visual-grounding-with-ibm-watsonxai)

**Legal and government projects and their extra requirements**
- UK National Archives "Find Case Law" (launched April 2022). Judgments arrive as Word documents and are parsed into **LegalDocML (Akoma Ntoso)**. A separate open-source **Judgment Enrichment Pipeline** marks up references to cases and legislation. A citation recognition and resolution engine was built with MDRxTech and vLex. Updates are published through an API and Atom feeds, which supports incremental ingestion. Computational analysis requires a transactional licence. **[snippet; 2022-2024 material, partly pre-2025]** — [Find Case Law API](https://caselaw.nationalarchives.gov.uk/the-find-case-law-api); [enrichment service repo listing](https://awesome.ecosyste.ms/projects/github.com%2Fnationalarchives%2Fds-caselaw-data-enrichment-service); [Mishcon event page](https://www.mishcon.com/news/events/current/bringing-structure-to-case-law)
- legislation.gov.uk point-in-time model. Timeline dates are the dates changes **came into force**, not when they were made. Changes the editorial team has not yet applied appear only in the "latest/prospective" view, not in point-in-time views. Versions start at 01/02/1991 (01/01/2006 for Northern Ireland). Akoma Ntoso XML is available with FRBR work, expression and manifestation levels, each with its own dates. **[snippet]** — [legislation.gov.uk AKN example](https://www.legislation.gov.uk/uksi/2002/249/data.akn); [OASIS LegalDocML thread on date semantics](https://www.oasis-open.org/archives/legaldocml/201412/msg00001.html)
- Laws.Africa editorial rule: one document per point in time, and amendments applied one at a time in chronological order. **[snippet]** — [Laws.Africa Editor Guide](https://docs.laws.africa/managing-works/amending-works/applying-the-amendments)
- "Grounded in Law" (PROPOR 2026) describes a production Brazilian legal RAG system: hybrid retrieval, grounded generation under citation constraints, and a post-generation **Reference Audit** layer that gives each reference a status and rewrites answers when inconsistencies are found. Telemetry: 184,895 audited answers and 43,175 extracted references. Legislation references resolve at 81.7% vs case law at 47.1%. Fidelity checks corrected 6.5% of checked answers before delivery. **[snippet; paper not opened, and it is unclear whether all figures share one denominator]** — [ACL Anthology 2026.propor-2.9](https://preview.aclanthology.org/new-sigs/2026.propor-2.9/)
- Harvard LIL "Open French Law RAG" is a case study on cross-language legal RAG with source-to-answer traceability. **[snippet, not opened]** — [LIL](https://lil.law.harvard.edu/open-french-law-rag/)

### Inferences
- For a legal or administrative corpus, a defensible 2026 setup has: (a) page-level routing (text layer → primary OCR/VLM → fallback engine → human), with field- or region-specific thresholds (stricter for article numbers, dates and citations, like A2I's 99% vs 90%); (b) a random sample sent to review regardless of confidence, for drift monitoring; (c) category-level gates for tables, multi-column pages, strikethrough or annotations, and cross-page tables, not a single average CER gate; (d) a fixed QA set run on both ground-truth text and pipeline output, reporting Δ context recall and Δ answer accuracy.
- Bounding-box provenance plus storing raw scans, OCR JSON and the final chunks is what allows citing back to page and box and auditing later. Docling's provenance ledger is a ready-made open-source pattern for a knowledge-graph target.
- Legislation needs a temporal model in addition to text: effective (in-force) dates, amendment application order, and unapplied changes flagged. Citation resolution success rate is itself a useful production metric (cf. 81.7% vs 47.1%).

### Gaps
- No primary 2025-26 source opened on idempotent reprocessing, content hashing, versioned re-indexing or cost monitoring for OCR pipelines. This area rests on general MLOps practice; I found no specific sourced write-up.
- No standard published recall@k/nDCG/MRR acceptance thresholds for OCR'd corpora.
- Annotation tools (Label Studio, CVAT, etc.) for OCR correction queues were not researched in depth. No sourced comparison.
- No published government pipeline that OCRs *scanned* legislation into RAG/KG with full evaluation numbers was found. The UK projects above start from born-digital Word/XML. CAP is the main large scanned legal corpus and has no OCR correction.
- I did not read the full papers behind "Lost in OCR Translation?", the PROPOR paper or the Docling paper.

## Q2. What numbers exist on how much OCR errors degrade retrieval and RAG, and on the cost of human review?

### Takeaway
On OHRBench, even the best OCR loses about 14% of end-to-end F1 vs ground truth (31.1 vs 36.1), with retrieval dropping from 70.0 to 59.2. Severe semantic noise roughly halves performance. On harder industrial documents (InduOCRBench, 2026), losses by category reach about 20-40 points of answer accuracy, and good CER does not guarantee good RAG. Reliable, independently measured human-review cost figures are scarce: what exists is vendor-sourced and directional only.

### Cited Findings

**OCR → RAG degradation**
- OHRBench overall F1: ground truth 36.1, Qwen2.5-VL-72B 31.1 (edit distance 0.18), MinerU 30.0 (ED 0.24), InternVL2.5-78B 29.6, Marker 29.5, GOT 24.6, Nougat 14.5. Best-tool gap: about 5 F1 points (~14%). Retrieval drops from 70.0 (GT) to 59.2 (best); generation from 43.9 to 37.5. Reading-order F1 for the best VLM is only 8.8. **[opened]** — [arXiv 2412.02592v3](https://arxiv.org/html/2412.02592v3)
- OHRBench, noise types: moving semantic noise from mild to severe (ratio > 0.6) causes a decline of nearly 50% for most retrievers and LLMs. Formatting noise mainly hurts multimodal questions, with maximum losses of 12.7% in retrieval (BGE-M3) and 9.1% in generation (Llama-3.1-8B), about 7% for larger LLMs. For tables, HTML retrieves worst and Markdown generates worst (it cannot represent merged cells). **[opened]** — [arXiv 2412.02592v3](https://arxiv.org/html/2412.02592v3)
- OHRBench appendix: Azure OCR (ED 0.17) loses 2.4 F1 with Qwen2-7B but 11.9 with Llama-3.1-8B, so the loss depends on the generator. VisRAG (image-based) scores 40.2 vs MinerU 37.9 vs GT 46.8. **[opened]** — [arXiv 2412.02592v3](https://arxiv.org/html/2412.02592v3)
- BM25 and BGE-M3 degrade similarly, so dense retrieval is not notably more robust to semantic OCR corruption. **[snippet, from a summary of OHRBench]** — [alphaxiv overview](https://alphaxiv.org/overview/2412.02592v4)
- InduOCRBench (570 docs, 3,402 pages, 12 industries). With PaddleOCR-VL vs ground truth: UltraWide ΔContextRecall −21.81 / ΔAcc −20.16; UltraLong −21.69 / −21.87; VisualStyle −10.56 / −41.19; MultiColumn −19.57 / −31.95; CrosspageTbl −11.10 / −22.03. GT text gives 100% RAG accuracy. The best OCR on UltraWide reaches 61.78% (gap of 38.22 points). OCR accuracy does not track RAG accuracy: VisualStyle has 82.9% OCR accuracy but only 52.8% RAG accuracy. Swapping retrievers (BM25, Qwen3-8B-Embedding) or using semantic chunking leaves the pattern unchanged (average gap 16.22% vs 16.72%). **[opened]** — [arXiv 2605.00911](https://arxiv.org/html/2605.00911)
- InduOCRBench, vision vs text: GPT-5 on page images scores 73.54% vs 52.92% on OCR text (with retrieval done over OCR text). Under ground-truth retrieval, vision scores 53.97% vs text 89.76%. **[opened]** — [arXiv 2605.00911](https://arxiv.org/html/2605.00911)
- "Lost in OCR Translation?" (May 2025): ColPali vision retrieval does well on documents like its fine-tuning data, but OCR-based RAG (Nougat, Llama 3.2 90B) generalises better to unseen documents of varying quality. The abstract gives no numbers. **[opened abstract only]** — [arXiv 2505.05666](https://arxiv.org/abs/2505.05666)
- Older CER-controlled IR studies **[pre-2025]**: retrieval effectiveness drops about −17% at a ~5% recognition error rate and about −46% at ~20%. Another study finds significant impacts starting at 5% error rate. **[snippet]** — [Univ. Neuchâtel](https://libra.unine.ch/bitstreams/4f793741-9562-4e07-b30e-e2ff64dab970/download); [PMC7148068](https://pmc.ncbi.nlm.nih.gov/articles/PMC7148068)

**Human review cost and automation rates (all vendor or secondary, low confidence)**
- Manual processing: $5-$25 per document vs $0.50-$2.00 automated. Error rates: ~0.5% automated vs 1-4% manual entry. **[snippet; vendor ROI calculator]** — [Hypersense](https://hypersense-software.com/idp-ai-automation-documents/roi-calculator)
- Per-page IDP platform pricing: ~$0.01-$0.05. Even the best tools route about 10-20% of pages to reviewers. **[snippet; blog roundup]** — [roundup](https://all-blog-master-crmlayers.pages.dev/ai-automation-tools/ai-document-processing-tools)
- Straight-through processing: vendors claim 85-95% **[snippet]** — [Savvycom](https://savvycomsoftware.com/?p=61018). Ardent Partners 2025 data on accounts-payable invoices gives an average of 32.6% and best-in-class 49.2% **[snippet, secondary citation]** — [imagetotable.ai](https://imagetotable.ai/blog/human-in-the-loop-document-review). These figures conflict, probably because STP is defined differently (extraction only vs zero-touch over the full cycle).
- Human-review charges and integration fees are often excluded from headline per-page prices. **[snippet]** — [Costbench](https://costbench.com/software/ai-document-processing/)

### Inferences
- Rule of thumb from the evidence: expect a 10-15% relative end-to-end loss from state-of-the-art OCR on mixed documents (OHRBench), and 20-40 points on hard layouts (wide or long pages, cross-page tables, strikethrough) (InduOCRBench). Semantic errors (wrong characters or numbers) matter more than formatting errors, which matters for legal text, where article numbers and dates carry meaning.
- Text-level metrics (CER, edit distance) are needed but not sufficient as gates. An end-to-end Δ-vs-ground-truth check on a domain QA set is the more reliable acceptance test.
- Human-review economics depend mostly on the share of pages routed. With pages at ~$0.01-0.05 automated, review is likely the dominant cost driver whenever the review rate exceeds a few percent. (This is an inference: no audited per-page reviewer cost was found.)

### Gaps
- No peer-reviewed or audited figure for human OCR review cost per page or minutes per page in 2025-26.
- No 2025-26 study sweeping CER levels against dense-retriever recall@k/nDCG. OHRBench uses synthetic noise ratios, and InduOCRBench does not report CER.
- No measured OCR→RAG degradation numbers specific to Vietnamese or other non-Latin legal scans were found.
